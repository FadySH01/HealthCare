Code defense · revision guide

What each component does

A plain-language walkthrough of your AERIX React pages, shared UI, browser-to-server connections, backend modules, and data flow.

How to use this guide
For every component, learn three things: what it is for, what data it uses, and what happens when the user takes an action. Then practise the short answers in the final section.

Project: AERIX healthcare-access pilot
Source reviewed: React/TypeScript frontend and JavaScript/Express backend
Important: This describes the code as it currently exists. It does not claim that sample providers are real partners.

The source files were reviewed without modifying app code.

01 · Start with the big picture

What kind of code is this?

The frontend is made of React components. A component is a reusable piece of the screen, written as a TypeScript function that returns JSX (HTML-like UI).

  • TypeScript: JavaScript with types. Types describe the shape of data and help catch mistakes while building.
  • React: builds the interactive pages from components.
  • Node.js and Express: run the backend and HTTP API in JavaScript.
  • MongoDB: document database supported for persistent data. Local demo mode stores sample data in a JSON file.
  • Vite: builds and serves the frontend assets.
src/main.tsx → App.tsx → page component → src/api.ts → /api endpoint in server/app.js → server/store.js → MongoDB or local demo file

Two meanings of “class”

In your frontend: most “components” are function components, like export function Assistant(). They are not old-style JavaScript classes. In JSX, className="panel" selects a CSS style; it does not define a programming class.
Actual backend class: LocalStore in server/store.js is a JavaScript class. It provides file-backed save, find, update and delete methods for the local demo.

Most important shared ideas

  • Props: information a parent passes into a component. For example, FacilityCard receives the facility to display.
  • State: a value that may change while a page is open. React re-renders when state changes. Examples: search text, selected date, chat messages.
  • Effect: code run after rendering for a task like loading data or registering cleanup.
  • Route: a page address such as /care.
  • API: a request and response used for the browser and backend to exchange data.
02 · App shell and reusable components

Files everything builds on

src/main.tsx · entry point

Finds the HTML root, loads fonts and CSS, then starts React and BrowserRouter. BrowserRouter makes client-side routes work without a full page reload.

Say: “main.tsx is the entry point. It mounts the React app and turns on routing.”

src/App.tsx · app shell and routes

Loads app configuration and the current signed-in account, puts shared data into Context, renders navigation and footer, and maps addresses to page components. It also defines login redirects for protected pages.

Say: “App.tsx is the main shell. It connects the shared navigation and app state to each route.”

src/context.tsx · shared app context

Defines the values multiple pages need: user, config, facilities, products, selected location, refresh, notifications, and login helpers. useApp() is a shortcut to read that shared context.

Say: “Context lets pages share the current user and common data without passing it through every component manually.”

src/pages.tsx · export hub

Re-exports page components from their files so App.tsx can import the routes from one place. It mostly organizes imports; it does not perform the page logic.

src/components.tsx · reusable UI

  • Brand: app logo linked to home.
  • PageTitle: consistent eyebrow, title, description and optional action for a page.
  • Status: styled status text.
  • Notice: information callout.
  • Empty: message/action for a page with no records.
  • Loading: loading indicator accessible as a status.
  • Modal: native dialog wrapper that opens on mount and closes through its handler.
  • FacilityCard: renders a facility card and calls the supplied booking action.
  • TextLink: styled reusable router link.

Say: “I split common UI into reusable components so pages stay consistent and avoid repeating the same markup.”

src/types.ts · data shapes

Defines compile-time shapes such as User, Facility, Product, Appointment, Doctor, AvailableTime, Order and Application. These help TypeScript check how frontend code uses data; server validation is still needed for real API security.

src/styles.css and public/ · appearance

CSS defines colors, layout, responsive behavior and component styling. Public SVG assets, web app manifest, icons and service-worker file support the installable visual shell.

03 · Main screens

What each page component does

Landing · src/landing.tsx

Public welcome page. Introduces the product, links people to the main tools, embeds nearby public hospital discovery, and submits limited product feedback through the API. The feedback message warns against entering medical information.

Home · src/care.tsx

Signed-in overview. Uses shared user/facility/location information, loads a patient’s requests, highlights the next appointment and provides entry points to care tools.

FindCare · src/care.tsx

Filters AERIX hospital records by search text, service, location and acceptance status. Optional browser location sorts by straight-line distance. It also displays nearby community map results; map listings are not automatically AERIX partners.

Booking · src/care.tsx

Dialog for choosing service, clinician, date and published time and requesting a visit. It loads clinician/slot options and sends POST /api/appointments. In-person requests still need clinic confirmation. Online demo navigation goes to a separate local demo page.

Appointments · src/journeys.tsx

Loads a patient’s visit and pharmacy requests, shows their current statuses, refreshes visible records periodically, and lets the user cancel through the API.

Pharmacy · src/journeys.tsx

Filters products by pharmacy, location, category, search and listed stock. A patient can submit a pickup or delivery-area request using POST /api/orders. The pharmacy must confirm availability; no payment or courier is booked.

NearbyPlaces · src/nearby.tsx

Reusable public map search for a hospital or pharmacy. It requests browser location only after a user action, calls GET /api/nearby, shows an OpenStreetMap embed, and prepares an enquiry for the user to copy/open in another app. It does not send the enquiry or confirm a booking.

Account and ProviderJoin · src/account.tsx

Account handles sign-in, registration, email code verification, sign-out-related account display and demo roles. ProviderJoin leads hospital/pharmacy applicants to the provider interest form. Server, not client form fields, decides which role is allowed.

04 · More screens and helpers

Safety, staff tools and shared logic

Assistant · src/assistant.tsx

Shows the chat interface, keeps its messages in React page state, accepts typed questions, can add speech-to-text using browser recognition, and can read replies through browser speech synthesis. The active send function calls the local offlineGuideReply().

Defense detail: the separate backend has an optional POST /api/chat endpoint, but this page’s current send handler does not call it. Explain the current behavior as the offline guide.

offline-guide.ts and health-dataset.ts

Hold curated general health information. The offline guide checks urgent phrases first, then matches common topics, and provides a safe fallback for unknown questions. The dataset contains topic overview, prevention, care and urgent-sign guidance with sources. This is prepared local content, not a diagnosing system.

Emergency · src/emergency.tsx

Collects a short situation, optional device location, optional photo and contact details. It builds a message for the user to review and open in email/SMS/WhatsApp. If email alert is configured, a separate consented API request can notify the configured inbox. That is not ambulance dispatch or a monitored emergency line.

Workspace · src/workspace.tsx

Role-specific clinic, pharmacy and admin interface. It loads the permitted data, calls protected API routes to manage requests, clinician availability, product listings and provider applications, and presents admin activity as allowed by the backend.

About and NotFound · src/about.tsx

About explains the product and collects provider interest; privacy mode presents safety/privacy content. NotFound is the fallback for an address that has no matching route.

OnlineVisitDemo · src/online-visit.tsx

Simulates a voice-style guide session with browser speech features and local prepared replies. It is a demo conversation, not a live doctor or actual video consultation.

api.ts · API/helper functions

  • api<T>(): sends JSON to same-origin /api, includes same-origin cookies and CSRF header when available, parses errors and returns typed data.
  • setCsrf(): remembers the server-provided CSRF token in page memory.
  • money(): formats numbers as currency.
  • prettyDate(): formats a date for display.

care.tsx small helpers

  • matchesLocation(): checks whether a facility matches selected city/country/all locations.
  • distanceKm(): uses the Haversine formula to estimate straight-line distance between coordinates.
05 · Backend pieces

What the server components do

server/index.js · start-up

Loads private local settings, selects preview/live mode, picks local or Atlas storage, seeds sample data only in demo mode, creates Express and listens on the selected port. Production startup checks that demo mode is off, a MongoDB URI exists and the app origin uses HTTPS.

server/app.js · API routes and server policy

Creates the Express app, installs request/security middleware, looks up sessions, defines authentication/role/CSRF helpers, validates inputs and exposes API routes for configuration, accounts, discovery, bookings, orders, providers, admin and optional chat. It serves the built frontend when available.

server/security.js · password/session utilities

Generates random tokens, hashes session tokens for storage, creates/checks salted scrypt password hashes, limits user information returned to the browser and holds system instructions for the optional AI endpoint.

server/store.js · persistence adapter

Implements LocalStore for a JSON file and createStore() for MongoDB. The adapter exposes common operations such as list, find-one, count, insert, update, remove and partner activation. Routes use this interface instead of directly choosing how each record is stored.

server/data.js · demonstration data

Provides illustrative locations and demo data. It helps the local walkthrough run without implying the records are real medical providers.

server/places.js · map-provider connection

Queries the shared public map service, normalizes/filters places and uses a short-lived cache and backup endpoint. It does not certify the real-world correctness of results.

server/verification.js and server/email.js

Verification creates/validates short-lived email challenges. Email helpers prepare verification, signup, provider, emergency and request notifications using configured transports. A successful connection/configuration check does not guarantee delivery into a user's inbox.

server/local-secrets.js and SETUP-*.ps1

Load encrypted Windows-local settings or host environment values. Setup scripts privately save database, AI or email credentials for this Windows account. Secret values belong on the server and should never be copied into frontend code.

More supporting modules

  • server/ai-errors.js: turns AI-provider failures into clear API errors.
  • server/atlas-dns.js: optionally configures DNS for Atlas lookups.
  • server/setup-admin.js: restricted one-time administrator setup utility.
  • server/seed.js: explicit sample-data seeding command.
  • server/check-*.js: integration configuration/connection checks.
  • scripts/dev.js: starts a safe local preview and rebuild watcher, selecting an available port.
06 · Prepare for questions

Short answers to practise

“What is a component?”
“A component is a reusable React function that returns part of the interface. Pages combine smaller components such as cards, notices and buttons.”
“What is the difference between frontend and backend?”
“The frontend is what the user sees and interacts with in React. The backend is the Node and Express server that validates API requests, applies permissions, and reads or writes application data.”
“How are they connected?”
“The frontend uses the shared api() helper to send JSON requests to same-origin /api routes. Express checks the request and access rights, uses the store adapter, then returns JSON for React to display.”
“Why TypeScript?”
“TypeScript lets us describe the data expected by components and API calls, which helps catch type mistakes during development. The server still validates data because browser types are not a security check.”
“What database does it use?”
“The project supports MongoDB Atlas. In the normal demo mode, it uses a local JSON file so sample workflows can run without Atlas. The selected mode controls where data is saved.”
“Are the hospital results verified?”
“No. OpenStreetMap results are community-mapped discovery listings and may be incomplete. They are not automatically AERIX partners, and an appointment is only confirmed after a participating clinic responds.”
“Does the health assistant use ChatGPT?”
“The active assistant page currently looks up prepared answers in a local health-topic dataset. An optional AI backend route exists, but the page’s current send function does not call it.”
“Does it make a diagnosis or book care automatically?”
“No. The guide gives general information and directs people to professionals. The app sends appointment and collection requests; providers still have to confirm them.”
“How do you protect accounts?”
“Passwords are stored as salted scrypt hashes, and sessions use HttpOnly cookies. The server also checks CSRF tokens, request input and role-based permissions. These are security controls, not proof that the whole service is risk-free.”
“What is one limitation or next step?”
“I would first connect the intended assistant behavior consistently and test consent, then complete provider verification and an end-to-end pilot with a real clinic. The sample workflow alone does not prove a real provider is available.”
Best defense rule: say what the source actually does. Be clear when something is a demo, a planned integration, or still unverified. Do not claim real providers, live AI, email delivery or emergency dispatch unless it has been checked.
