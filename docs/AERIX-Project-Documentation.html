01 · Executive overview

What AERIX is

AERIX is a healthcare-access pilot that brings care discovery, appointment requests, pharmacy collection requests, provider tools, and general health information into one web app.

The project has a responsive React and TypeScript interface and a Node/Express server. The same server serves the built web pages and the JSON API. MongoDB Atlas is supported for persistent database storage; a local JSON-file store supports demonstrations.

Visitor or signed-in user → AERIX web app → Express API → local demo storage or MongoDB
Overall review: The production build succeeded. The repository describes a functional pilot workflow, not a verified, live hospital/pharmacy network or a clinically certified medical product. Sample providers and public map results must not be represented as confirmed partners.

At a glance

  • Patient, clinic, pharmacy and administrator journeys.
  • Facility discovery using OpenStreetMap community listings and AERIX partner catalogue data.
  • Appointment requests with clinic review, plus pharmacy collection requests with staff updates.
  • Email-verification account flows and role-based workspaces.
  • Offline general-health topic guide, plus a separate server endpoint for optional OpenAI responses.
  • Emergency message preparation, optional email alert, and provider-interest review workflow.

02 · Product and journeys

What someone can do

Explore and find care

The welcome page explains the pilot and offers hospital discovery. Signed-in pages show AERIX catalogue facilities and partner workflows. Nearby results come from public OpenStreetMap data, which can be incomplete or out of date.

Request an appointment

A patient selects an eligible clinic, clinician and staff-published time, then sends a request. Clinic staff can confirm, complete or update it. The request is not a booking until the clinic confirms it.

Request a pharmacy collection

A patient can request a non-prescription catalogue item for review. Pharmacy staff update readiness and collection status. The app does not process payments, book couriers or atomically reserve stock.

Manage an account

Account pages support registration, sign-in and email verification. Clinic, pharmacy and admin roles receive dedicated workspace tools. Role checks are enforced in the server API.

Use the health guide

The current assistant page selects a general-information answer from a local curated health dataset. Browser speech can dictate text, and browser speech synthesis can read answers aloud where supported.

Prepare an urgent message

The emergency page can prepare a message for the visitor to send using their chosen contact app, and can offer an email alert when configured. AERIX does not dispatch an ambulance or guarantee the alert is read in time.

Register provider interest

A provider can apply to join. An administrator reviews and enters verification details before activation; activation alone does not verify an actual licence. New facility requests remain paused until staff set them up.

Share product feedback

The public welcome page accepts limited feedback and warns people not to include health information. Administrators can review submissions.

Map listings are discovery, not partnership. Phone numbers, hours, licences, services and availability in public map data are not independently confirmed by AERIX. Call before travelling.

04 · Server and data

What runs behind the pages

The app is served as one Node service: Express handles /api and returns the React build for page routes. A static-file upload of dist/ alone cannot provide sign-in, saved bookings, workspace actions or other server features.

Local preview and Atlas

  • Standard preview: npm run dev forces demo mode and persists demonstration state in .data/demo.json. The included providers/accounts are samples.
  • Atlas preview: npm run dev:atlas opts into the separate aerix_demo database. It must not point sample data at the live aerix database.
  • Live mode: requires correctly configured private MongoDB, HTTPS and demo mode disabled. A successful connection check does not by itself validate production workflows.
  • MongoDB indexes cover unique accounts, session expiry, active booking conflicts and frequently queried facility, product, clinician and appointment data.

External services

OpenStreetMap Overpass

Community-mapped nearby hospital and pharmacy discovery. Shared service; results can be missing, old or unavailable.

OpenAI API

Optional server-side endpoint exists. It requires authenticated, consented API requests and a private server key. The current assistant page does not call this endpoint.

Email delivery

Optional Gmail SMTP or Google Apps Script HTTPS sender supports verification and notifications, subject to setup and real inbox testing.

Browser features

Geolocation, speech recognition, and read-aloud features depend on browser support, permissions and—in some cases—an external browser service.

05 · Accounts and protection

Implemented security foundations

  • Passwords use salted, expensive scrypt hashing; plaintext passwords are not saved as account records.
  • Sessions use random tokens; the server stores a digest and places the raw token in an HttpOnly, SameSite cookie. Production cookies are Secure and use the __Host- prefix.
  • Authenticated changes require a session-bound CSRF token. Requests are checked for expected content type, application request header, allowed origin and cross-site metadata.
  • Strict request schemas reject unexpected fields. The server enforces roles and checks access to individual records.
  • Helmet adds security headers; request bodies and API traffic are size-limited and rate-limited.
  • Windows setup scripts encrypt local secret values with DPAPI for the current Windows user. Deployment needs separate host-side secrets.
  • The React interface renders assistant output as ordinary text. The guide is framed as general information, not diagnosis or prescribing.
Privacy behavior: Device location is requested after a user chooses it. Nearby-search coordinates are rounded for lookup; emergency page coordinates remain on the device unless the user chooses to email an alert. Current guide conversation content is held in the open page, not deliberately saved to the AERIX collections.

Security still needing completion

These protections are useful implementation controls, but they are not proof that the product is “unhackable,” independently audited, compliant with every jurisdiction, or safe for unsupervised medical care. The documentation identifies password reset, staff/admin MFA, account export/deletion, shared rate limiting, operations monitoring, backups/recovery, clinical review and independent security/accessibility review as further work.

How to run the local demonstration

  1. Open a terminal in C:\Users\HomePC\Desktop\AERIX.
  2. Run npm run dev and wait for the local address printed in the terminal.
  3. Open that address in a browser; keep the terminal open during the demonstration.
  4. Use the demonstration roles for a walkthrough and stop with Ctrl+C.
Do not publish the demo with public administrator shortcuts, share .env or .secrets, or treat fictional catalogues as actual care capacity.
07 · Findings and next steps

Important review findings

1. Health-guide UI and backend are out of sync. In src/assistant.tsx, the send action directly calls offlineGuideReply(); it does not call /api/chat. The current screen claims local/offline replies and no server transmission. The backend AI route exists separately. Any plan to show live AI must first connect the page, implement explicit consent/status handling, reconcile the privacy text, and check the AI connection state.
2. README and some docs are stale. The README describes an AI conversation with consent and a server request, but the active page uses the offline guide without that call. Treat the currently compiled source as the description of actual behavior.
3. “Email configured” is not “email delivered.” Sender setup and connection checks need a controlled real signup/inbox test.
4. Map results are not verified partners. The pilot is not yet a live care network, even where search listings exist. Actual bookings need an onboarded provider and staff response.
5. Emergency tools are contact aids. An accepted email alert does not dispatch emergency services and may not be read immediately.

Practical order for completing the pilot

  1. Decide whether the health guide is intentionally offline-only or should provide optional online AI, then align page behavior, explicit consent, privacy copy, README and backend status.
  2. Run the existing automated suite and record its result alongside the successful build.
  3. Complete controlled end-to-end account verification and email-delivery checks without real patient details.
  4. Onboard one hospital and one pharmacy only after independently confirming contacts, licences, staff access and service workflows.
  5. Test the appointment request/confirmation and pharmacy request/collection journeys with participating staff.
  6. Before public health use: obtain clinical review, complete recovery and staff MFA work, define privacy/retention procedures, enable HTTPS, and do independent security and accessibility reviews.

Explicitly outside the verified scope

The production build only verifies TypeScript compilation and bundling. It does not prove a live Atlas connection, delivered email, live AI response, a verified partner, real availability, a dispatched emergency alert, secure hosting configuration, clinical safety or regulatory approval. These need their own explicit live checks.
